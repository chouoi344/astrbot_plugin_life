# 第 4 轮修复与对抗性审查报告

本轮按“首次启动修复 → 交叉对抗性审查 → 全套验证”执行。代码位于指定的 `新插件/astrbot_plugin_life_scheduler_plus/`。真实 AstrBot 安装、配置和运行数据均未修改，未执行安装或卸载操作。

## 一、各项修改与对应测试

### 1. 首次档案优先，失败后日程继续

- 所有首次日程入口统一经过空档案检查：启动、定时、视图读取及手动生成都会先等待本轮档案任务。
- 档案成功后，日程读取已经保存的档案和提取出的城市；档案本轮失败或执行超时后，日程照常生成，记录等待后补齐的标记。等待下一次档案自动重试不会挡住日程。
- 图片扫描仍为受管理的独立任务，其模型调用也经过统一队列。
- 对应：`test_round4_engine.py::test_every_schedule_entry_waits_for_first_profile_and_uses_its_city` 的多入口实例、`test_failed_first_profile_still_generates_fallback_day_without_waiting_for_retry`；`test_round4_audit_engine.py::test_each_first_schedule_entry_proceeds_after_non_json_profile_failure` 的四入口实例。

### 2. 插件级模型队列

- 新增 `core/model_queue.py`，本插件的档案、日程、回顾、模拟天气、聊天判断、意外和衣柜识图统一经过同一个执行队列，同时最多执行一个模型请求。
- 空档案请求优先取得首轮机会；之后按空档案、聊天、普通请求轮转，同类按先来先到执行。正在执行的请求先结束，避免后来请求持续插队导致某类工作永远排不到。
- 排队不启动执行计时。取消等待者会移除队列项；取消已经获得执行机会的任务会释放位置；插件关闭会取消并清理本插件持有的模型任务。
- 识图中的 JSON 修复复用同一个位置和总预算，避免嵌套入队死锁或第二次调用重新获得完整预算。
- 对应：`test_round4_model_queue.py`；独立的 `test_round4_audit_queue.py`。后者专门在“已经授予执行机会、任务尚未恢复”的间隙插入取消或关闭，并检查后续请求仍能执行。

### 3. 按用途设置执行超时

执行预算集中在 `core/llm.py::MODEL_TIMEOUTS`：

| 模型请求用途 | 执行预算 |
| --- | --- |
| 档案、日程、默认生成 | 180 秒 |
| 聊天判断 | 60 秒 |
| 小意外、独立长期事件用途 | 120 秒 |
| 回顾、模拟天气 | 120 秒 |
| 衣柜识图整个整理流程 | 195 秒 |

计时从取得执行机会后开始；准备模型图片、格式修复及本次调用内的连接重试都在对应执行预算内。临时会话清理另有最多 5 秒的清理保护。错误说明使用实际触发的时限，图片准备等更短的独立保护仍会显示其实际时限。

当前长期事件由日程响应中的 `new_events/event_updates` 一并输出，因此该组合请求使用主用途日程的 180 秒。独立 `event` 用途策略为 120 秒，当前未为它额外拆分模型请求。

对应：`test_round4_model_queue.py::test_purpose_timeouts_show_actual_budget_and_original_cause`、`test_queue_wait_does_not_spend_the_chat_execution_deadline`、`test_outfit_json_repairs_share_one_slot_and_one_deadline`；`test_round4_integration.py::test_real_profile_execution_timeout_counts_failure_and_unblocks_schedule`。

### 4. 档案后来成功，自动补齐未来日程

- 当天数据新增 `profile_missing_at_generation`，表示生成时使用了空档案。
- 档案成功后刷新提取城市的天气，并触发当前业务日的后补齐；档案成功早于旧日程提交时，也会在旧任务完成后再次检查，覆盖两种完成顺序。
- 后补齐保留原 `plan`、已经过去的实际记录、原变更记录及约定。提交时读取最新 `actual` 和约定，保护模型等待期间新记录的聊天安排与到期约定所在段。
- 成功后清除标记，在 `changes` 写入来源 `admin`、说明“档案生成后补齐”。失败时保留旧日程、记录独立修复状态，并按冷却重试；页面仍显示旧时间轴和重试入口。
- 对应：`test_round4_engine.py::test_later_profile_success_enriches_future_and_protects_plan_past_and_promises`、`test_failed_profile_enrichment_keeps_old_day_and_retries_after_transient_cooldown`、`test_profile_finishing_before_empty_profile_schedule_commit_still_triggers_backfill`；独立的 `test_round4_audit_engine.py::test_backfill_queued_before_chat_commits_protects_latest_chat_and_pending_due_slot`、`test_backfill_transport_failure_preserves_facts_and_resumes_after_reload`。

### 5. 重载或卸载取消的尝试退回计数

- 开始时保存自动计数的预扣记录，真正取消时退回对应预算。排队中取消与模型执行中取消采用同一处理。
- 启动和读取生成入口都会恢复遗留的 `generating`，兼容有预扣字段的新记录及旧格式记录；恢复完成会清除预扣标记，避免重复退回。
- 执行超时属于一次实际失败，正常计数；插件取消则退回。手动重试继续不消耗自动额度。
- 自动限制的范围明确为：档案每个自然日最多 3 次；普通日程每个业务日最多 4 次尝试；窗口修复和档案后补齐各自沿用最多 4 次自动修复预算。这些计数不是所有模型调用的总数，单次尝试内的格式修复也可能产生后续模型请求。
- 对应：`test_round4_engine.py::test_reload_cancellation_refunds_auto_attempt_and_restart_runs_again`、`test_hard_exit_generating_reservation_is_refunded_once_before_retry` 的多格式实例；`test_round4_audit_engine.py::test_last_automatic_attempt_cancelled_in_queue_refunds_once_and_cap_still_applies` 的档案/日程实例。

### 6. 临时故障快速重试

- `core/errors.py` 集中区分超时、连接错误和临时服务错误，支持异常链及临时服务状态。
- 临时失败按 2、10、30 分钟递增；配置错误和内容问题保留原间隔，档案为 30 分钟、日程为 10 分钟。达到自动上限后保留中文提示和手动入口。
- 对应：`test_round4_model_queue.py::test_transient_failures_back_off_fast_and_content_errors_keep_old_interval`；`test_round4_engine.py::test_transient_failures_back_off_two_ten_thirty_minutes_and_content_keeps_old_interval`；真实适配器执行超时后日程放行的集成测试。

### 7. 界面状态一致，长排队仍能自动更新

- 自动、手动、排队中的档案任务统一显示当前生成状态，隐藏旧失败原因、旧重试时间及旧次数提示。日程同样处理。
- 手动点击后立即更新状态，处理 POST 尚未返回、GET 旧数据迟到、离页和浏览器缓存恢复等情况。
- 衣柜识图改为后台受理并返回带类型的任务编号；通过 `tasks/get` 观察结果，整段排队不受前端普通 POST 的 210 秒上限影响。真正执行识图时才启用 195 秒预算。
- 档案任务与识图任务按类型隔离；任务结果只投影穿搭字段，临时文件路径留在服务端。取消、失败、重载会清理本插件的临时图片。
- 保留日程前 3 分钟的快速查询、档案前 4 分钟的快速观察；较慢时切换为每分钟确认到终态或离页。这样档案 180 秒加日程 180 秒、或排队较长时，完成后仍能自动显示。
- 对应：`test_round4_api.py`、`test_round4_frontend.py` 和独立的 `test_round4_audit_ui.py`。虚拟时间测试包含超过 210 秒的识图排队、超过 3 分钟的日程以及超过 4 分钟的档案自动完成。

## 四、用户实机确认步骤

1. **更新并保留资料**：先按 README 的“更新插件，保留档案和衣柜”备份配置与数据，再使用适合当前版本的更新方式。更新完成后，打开生活档案和衣柜，确认旧资料仍在。更新现用实例时保留插件，使用更新或代码覆盖流程。
2. **全新安装自动出现**：在本来就没有资料的测试安装中，先配好可用模型和人设，再安装插件。打开视图后**不点任何生成或重试按钮**，应先看到档案正在生成，随后日程准备；网络和模型正常时，几分钟内档案与日程都自动出现。较慢时可继续等待低频观察，完成后仍会自动显示。已有资料的现用实例无需清空来做这项测试。
3. **首次生成中重载**：在上述测试安装第一次生成开始后约 30 秒，使用插件的“重载”，保留配置与资料。重新打开视图，任务应自动重新开始；这次取消会退回自动额度，随后档案和日程仍能自动出现。
4. **模型暂时连不上**：遇到真实连接故障时，档案页应显示中文原因和重试入口；今日日程仍会继续尝试生成。故障恢复后，等待自动重试或手动点重新生成，生成中应只显示当前进度，旧失败和旧重试时刻消失。
5. **档案后来成功后的补齐**：如果此前已有空档案生成的日程，档案成功后等待自动补齐。查看今日日程，过去的活动仍在，未来安排与档案相符；已有聊天约定仍保留，天气按档案提取的城市刷新。补齐失败时，旧时间轴继续显示，并有失败原因和立即重试按钮。
6. **排队识别图片**：档案或日程正在使用模型时，在衣柜上传图片并点 AI 提取。应先显示等待/处理中，完成后填入穿搭；排队较久也会继续等待。换图或关闭编辑框后，旧结果不应覆盖新内容。
7. **切换与返回页面**：生成中切到其他板块或关闭视图，再返回。应显示当前后台状态；页面恢复后迟到的接受结果也应切到正在生成，不会残留旧失败提示。生成结束后应自动出现新内容。
8. **时间核对**：电脑保持 Pacific 时区，AstrBot 保持 Asia/Shanghai。时间轴、当前活动和自动重试时刻应按 AstrBot 的业务时区显示。

配置、网络或模型持续有问题时，以页面的中文提示和手动入口处理；这些操作不要求读取日志或修改内部计数文件。
